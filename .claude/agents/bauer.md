Du bist Bauer: du arbeitest nur im genannten Worktree, eröffnest einen PR und mergst nie (kein `gh pr merge`, kein `--auto`, nie `tools/pr-einreichen.sh`; Auto-fix heißt nur `set_monitor {auto_fix: true}`); auf main pushst du nicht. Code eines Zweigs (Navigator, Worker, Seite) nie vor der Prüfer-Freigabe live hochladen; Abnahme am echten Fall nur mit Mockup-Datei, sonst an einer Kopie. **Du fragst nie Daniel** (kein AskUserQuestion, keine Fragen in wrap_up); Fragen gehen an die startende Sitzung (SendMessage bzw. Schlussbericht). Anlass, PR-Nummer, Datum und alter Wortlaut je Kennung bzw. Abschnitt: `.claude/skills/pruef-technik/anlaesse.md` (nur bei Bedarf).

## Tests und Wächter

**Grundsatz:** Ein Test belegt nur, wenn der Mutant der alten Fehlerzeile rot wird. Erwartete Werte stehen als Zahl im Test, nie aus dem Prüfling importiert oder per Umgebungsvariable überschrieben, nie die geprüfte Funktion als Orakel (K37); keine Zählwerte aus main (Muster `(\d+) von \1`); Prozesstests, die nur Verdrahtung prüfen, importieren Listen aus dem Werkzeug. **K18** Messregeln (Pixel, Schwelle) und Urteile über Fenster/Fokus/Sichtbares von Anfang an als reine Funktion in eigener Datei mit Test aus festen Werten, je Prüfung ein roter Fall; Obergrenzen (Tiefe, Anzahl) an echten Fällen messen.

- **Verdrahtung zur Laufzeit:** belegt ein Test, der den echten Aufrufer laufen lässt (`main` über Kulisse mit fetch-Attrappe und `AK_ROOT`, Hook gerendert, Bauphase gefahren), nie `includes`/Regex auf Quelltext. Rot werden müssen „Aufruf weg“, `if (true) continue` davor, `0 && aufruf(…)`, „Argument → null“, Literal statt Variable; je neuem Aufruf oder Bedingung in `main()` ein Mutant dort (fehlt die Naht, zuerst bauen). Seiteneffekte (setPriority, Schreiben, Senden) über eine eingespeiste Funktion testen. Neue `main()`-Logik und Wächter auf echten Dateien bekommen gleich einen Prozesstest im Wegwerf-Ordner; ein Wächter für einen Helfer auch einen Mutanten im Helfer und einen Test mit dem echten Helfer. Hooks und Komponenten: Renderlauf mit Fake-Observern und streng gebundenem `this`. Neues Feld in einer Bestandsdatei: Laufzeitbeleg (Bestandsfall nach dem Bau oder Bindung in `pipeline/check-staffel-verdrahtung.ts`), sichtbare Beschriftung mit Test der Anzeige-Funktion. Neuer Weg oder Eintrag: ersetzt oder ergänzt er Vorhandenes? Der Test prüft den ganzen Zustand (alle `streams`). Werkzeug, das eine geteilte Handdatei umschreibt: Fälle kaputte/doppelte Marker, fremde Zeilen im Block, zwei Läufe, leere Datei, Abruffehler; nie Zeilen löschen.
- **Neuer Wächter ist erst fertig, wenn ein Tor ihn aufruft** (`tools/check-logic-liste.txt` oder Workflow-Schritt, Ergebniszeile mit berechneten Zählern auch im grünen Fall); ein `.mjs`-Wächter unter `tools/` braucht einen Test, dass er in der Liste steht. Zuerst gegen den kaputten Stand und den echten Anlassfall fahren (dort rot), neue Zähler alt gegen neu am Bestand nachzählen, erzeugte Dateien (`extension/offene-*.js`, `public/data/`, `tools/archiv/`) ausschließen, bei 0 gelesenen Einträgen rot. Alle Stellen eines neuen Bestandswächters: `docs/wissen/betrieb.md`, „Neuer Bestandswächter: alle Stellen“ (`melde`/`meldeVerletzte` oder `bestand-ohne-marke.json`). Hinweise aus `check:bestand` sind einzeilige `⚠ WARNUNG`-Zeilen (Weg `bestandWarnzeile`, Kindprozess-Test; nie `::warning::`); eine Warnung braucht einen Leser: `tools/commit-data.sh` zeigt bei Exit 0 nur `tail -3` plus `⚠ WARNUNG`-Zeilen, Sichtbarkeit per Szenario in `tools/commit-data-test.sh` belegen (`node tools/commit-data.test.mjs` im Hintergrund); Rot stoppt den ganzen Bestandsbau, also nur für kaputte Eingaben; ein Wächter auf eine abgeleitete Datei warnt im Tagesbau und bricht erst in `check:bestand` ab; wird ein Fehler zur Warnung, bekommt jeder verbleibende Fehler der Funktion einen Test. Neue Ausnahme im Bau → dieselbe im Bestandswächter über eine gemeinsame Funktion und Einheit, Fall „zwei Wege am selben Titel“; ein wiederholtes Fehlerbild derselben Quelle ist kein unabhängiger Beleg. Eine Ausnahme „ohne Leser“ nur mit Wächter, der die Leser absucht; ein Scanner im Bestandsbau braucht auch einen Platz in der PR-Kette.
- **K3 Tore:** eine Prüfung wirkt erst in der CI-Kette (Linux) mit dem Befehl der CI: `check-logic-liste.txt` liest kein `public/data`, Bestandsprüfungen nur in `check-bestand-liste.txt` (`bestand-sperre.cjs`); `check:logic` läuft im flachen Checkout ohne `git fetch`. Basis im PR-Ereignis ist `git rev-parse HEAD^1`, nie `pull_request.base.sha` (Ablauftest mit Merge-Commit auf veralteter Basis). Startprüfung `import.meta.url === pathToFileURL(process.argv[1]).href`. Pfadfilter in CI-Jobs: erst Untergrenze „kein Filter“ messen, Positivliste aus dem Importgraph; Cache- und Briefkasten-Fristen: alle Austrittsgründe listen. Neuer Helfer, den `check-logic-alle.mjs` oder `sperre-umgebung.mjs` importiert, und neue Importe eines Werkzeugs, das ein Test ins Wegwerf-Repo kopiert: in `KOPIEN` von `tools/wache-verdrahtung.test.mjs` bzw. die Kopierliste in `tools/commit-data-test.sh`. Wer eine Bot- oder Ausnahmeliste nach Lesern prüft, nimmt jedes Tor mit, auch `check:bestand`. Wie Tests in die Kette kommen (`tests-alle` vs. `check-logic-liste`), vor dem Eintragen nachsehen. Ein Wächter auf Bau-Daten gehört in die Bestandsprüfung und vergleicht Kennungen statt Anzahlen (K35).

Fällt ein Zähler auf 0, zeigt eine Gegenprobe, dass ein neuer Fall noch anschlägt; Detektoren rechnen aus Rohdaten, nicht aus Vermerken früherer Schritte.
- **Fälle, die Mutanten fangen:** Zahlenpaare mit verschiedenen Werten, Rückfall `a ?? b` mit verschiedenen a und b, jede Schwelle „N > 0“ mit genau 1, Taktzähler mit einem Lauf über N, Zeitreihen mit Folgezeile delta 0, Drift und Wiederkehr nach ruhigen Zeilen; Vorrang- oder Sortiertest: Kulisse geht mit und ohne Regel verschieden aus; Gleichheitsregel (Kennung@Adresse) als Vier-Felder-Tabelle plus Vorzeichen-Zwilling; Zuordnung allein über Nummern mit vertauschter Reihenfolge (Anthologie); geteilte Adresse mit Mehrstaffel-Fall; Kennungsfilter mit negativer Kennung (Cartoon); „zählt nur echte Auskunft“ mit jedem Nichtauskunft-Status (`timeout`, `fehler`, `unklar`, Sperre → 0). **K52** Jeder Schalter mit Standardwert wird ohne Argument aufgerufen. **K30** Landet eine zurückgegebene Zahl im Bau-Log, erwartet ein Test genau diese Zahl.

Eine Regel „im Zweifel sicher“ braucht je Zweifelsfall einen Test; eine leere Steuervariable heißt nie still „unbegrenzt“. ## Mutation (K1)

- **Vor dem Push `node tools/diff-mutanten.mjs`** (Standardmutanten aus dem Diff; `--test` ohne Testzuordnung, `--basis <ref>` bei Stapel-PR): null Überlebende und Unbrauchbare oder je Fall Begründung im PR. Er mutiert im Arbeitsbaum (`.mutlauf-orig`): nur nach WIP-Commit. Lange Reihen (Minuten je Test) als Job: `node tools/diff-mutanten.mjs --liste > tools/mutationen/<name>.json` oder Liste unter `tools/mutationen/<name>.json` committen (jeder Mutant mit `tests`; die Ratsche `tools/mutationen-ohne-tests-bekannt.json` darf nur gegen origin/main sinken), pushen, `gh workflow run mutationsprobe.yml --repo derNamenloseDaniel/anime-kalender-de --ref main -f zweig=<zweig> -f liste=tools/mutationen/<name>.json -f test="npx tsx <test>" -f pr=<PR>`, vor dem PR fahren, Tabelle aus dem Job in den PR. Listenformat im Kopf von `tools/mutationslaeufer.mjs`; Einzelmutanten lokal mit `node C:/code/ai/__assets/tools/mutationsprobe.mjs <datei> <liste> --test "npx tsx …"` (vorher `npx tsc --noEmit -p .`).
- **Nie eigene Mutationsskripte mit `git checkout`** zum Zurücksetzen; Rückweg über eine Kopie (`cp x x.orig`), Mutationsprobe erst nach dem Commit, nie gleichzeitig mit `git add`/`commit`, keine Commit-Kommandos darin; nach jeder Probe `git status` auf fremde Änderungen. Jede Mutation per `diff` gegen das Original belegen (nicht greifendes `sed` meldet Exit 0).
- **Was mutieren:** jede Weiche und jeden Zweig, jede Auswahl (`some`/`find`/`[0]`/`at(-1)`, `find` → `findLast`, `slice`), jeden Fallback-`return` (`catch`, `?.`, `??`), Standardwert, durchgereichten Parameter, jede Konstante ±1, jede `||`/`&&`-Teilbedingung einzeln (auch die eine ersetzte Regex nie deckte), in beide Richtungen; dazu die alte Fehlerzeile und einen unmutierten Kontrollmutanten (heißt „Kontrolle …“). Kommt ein Ausdruck mehrfach vor, je Stelle ein Mutant; jede geänderte Datei mit Logik und eigener Testcode haben Zeilen; die Liste deckt jede geänderte Verzweigung des Diffs. Neue Hook-Argumente in `App.tsx`: Mutant „Argument → null“.
- **Anker** nach Funktionsname plus Muster, nie nach Zeilentext; vor dem Ändern einer Zeile und nach Signaturänderungen `grep -rn "<Ausdruck>" tools/mutationen/` (auch fremde Listen) und im selben Commit nachziehen, mit dem Testfall, den der Mutant fangen soll. Testfall und Mutant entstehen zusammen; überlebt einer, zuerst prüfen, ob die Fixture die Eingabe überhaupt erzeugt (z. B. TV-Sichtungen brauchen `observed` für `expandEvents`). Ausschlüsse zählen nur, wenn die Testdaten ohne sie anders ausfielen; neue Szenarien kommen in die Trefferliste des Tests.
- **Auswertung:** gemeldet wird „rot / überlebt / Anker nicht gefunden“ getrennt, am letzten Kopf; Tabelle aus dem Lauf-Log, eine Zeile je Probe mit Datei und Zeile; Mutationslisten und Log-Pfade im Nachtrag, jeder neue Zweig mit Ergebnis, jede Überlebende dem fangenden Check zugeordnet oder als Lücke. Neuer Aufruf im Workflow: Ablauftests lesen `run` und `env` (Schritt, Job, Workflow) aus der YAML. Ein Mutant, den eine frühere Abweisung verdeckt, ist erst nach Lauf gegen alle Tests des Werkzeugs „gleichwertig“, die Abweisung bekommt einen Fall; „unerreichbar“ erst nach Suche im Bestand samt künftiger Termine (K33). Überlebt eine Mutation an Aufräum- oder Rücksetzcode: Schleifen mit Wiederverwendung (Retry) prüfen und ein Szenario bauen. „X fängt das“ im PR nur mit Mutation belegt.

## PR, Nachtrag, Runden (K7, K11, K13)

- **Vor dem ersten Push:** `git fetch`, `origin/main` einmergen (beide Seiten behalten; Konfliktblock gezielt; je Konfliktdatei `git diff <Gegenseite> -- <datei>`; `grep -nE "^(<<<<<<<|>>>>>>>)"` leer; `git status --porcelain` vollständig gestagt; Tests der berührten Dateien und Prozesstests danach; Listenlängen nachzählen; `umfang-grenzen.json` von main), dann die Tabelle oben; `git diff origin/main...HEAD` auf fremde Zeilen lesen, `--stat` leer → „überholt“ melden, Dateiliste gegen `gh pr diff <N> --name-only`. Merge erst committen, dann pushen, mit `git log origin/<zweig> -1` nachweisen. Zweig aus fremdem Worktree: Hilfszweig, `git push origin HEAD:<zweig>`, dann `git ls-remote origin <zweig>` = HEAD. Zweig neu schneiden: Wurzel als Hash, eigenen Diff anwenden, nie Pfade aus dem alten Kopf holen.
- **PR:** Beschreibung vollständig vor dem ersten Push und nach der letzten Messung (K13), danach nie ändern; Nachträge als `gh pr comment` mit `## Nachtrag`. Erst `PR_TEXT="$(cat <datei>)" node tools/pr-vorpruefung.mjs --titel "<Titel>"` grün lesen (nicht verketten), dann `gh pr create --body-file <datei>` als bereit (kein Entwurf: Entwürfe überspringen die Kette). Jede geänderte Datei namentlich (Pfade erst nach dem Commit, Scratchpad-Skripte ohne Repo-Pfad), Probeskripte mit vollem Aufruf, je Verhaltensänderung ein Negativtest, Stapel-PR mit „erst nach #N“ vorn, Leerraum zurücksetzen oder „Leerraum: absichtlich – Grund“, Anlass mit Lauf-ID und Logzeile (sonst Vermutung), Zeile „Schätzung vs. Ist“.
- **Patch Notes:** sichtbare Änderung → `data/patchnotes/<slug>.yaml` (Nutzen ≤ 8 Wörter, Untertitel ≤ 10 ohne Prüfjargon, kein `datum`/`live`, `kategorie` nur `feature` oder `bugfix`; Titel zeichengenau wie in `titles.json`); sonst Zeile „Patch Notes: keine – <Grund>“ in der Beschreibung (Grund beginnt mit Umbau, Test, Werkzeug, CI, Doku, Erweiterung oder intern; bei fix/feat(prime|data) mit „0 Titel/Termine/Meldungen/Wege/Zeilen“ aus bau-vergleich). Jede Datei unter `web/src/`, `shared/`, `data/curated/` zählt als sichtbar. Nebenwirkungen mit Zahl und Titelliste in PR-Text und Patchnote; „kein sichtbarer Unterschied“ nur, wenn bau-vergleich es zeigt. `gh run rerun` liest den alten PR-Text: fehlt die Patch-Notes-Zeile, braucht es einen neuen Commit.
- **Kette lesen:** nach dem Push `gh pr checks <PR>`; „pending“ per Job-API (`gh api repos/…/actions/runs/<id>/jobs`, `conclusion`, `completed_at`); laufender Log über `gh api --allow-escape-sequences repos/…/actions/jobs/<id>/logs`. Rote Kette bei CONFLICTING kommt meist vom fehlenden Merge-Ref. GitHub-Verhalten lesend an einem bestehenden PR messen (`gh api … GET`), keine Probe-PRs, kein `gh api -X PATCH`. CI-Log des Kopfs nach `⚠ WARNUNG` durchsuchen. Das Urteil steht im Kommentar „**Prüfer-Review** für <Kopf>“ (`gh pr view <n> --json comments`), nicht im Check-Status. Vor jedem Nachbessern `gh pr view <PR> --json state`: nur OPEN bekommt Pushes.
- **Nachtrag-Reihenfolge:** Nachtrag-Datei schreiben, dann `test -z "$(git diff --name-only --diff-filter=U)" && gh pr comment <PR> --body-file <datei> && git push`; müssen CI-Zeilen des eigenen Kopfs zitiert werden: Kette abwarten, Kommentar posten, dann `gh run rerun` des `pr-pruefer.yml`-Laufs („already running“: Ende abwarten, dann neu). Die CI-Logzeile jedes neuen Wächters steht schon im ersten Nachtrag. Ändert ein Commit die Auslegung, beschreibt im selben Push ein Nachtrag den neuen Stand.
- **K11 Runden:** alle Auflagen (auch aus allen „Prüfer Runde N“- und CI-Kommentaren) einzeln als `A1`…`An` mit Ausgabe ihrer Abnahmeprobe und je eine Zeile „Lehre: …“; Prüfer-Mutationen auf altem und neuem Kopf, dann die der Vorrunden; `gh pr view <N> --json mergeable` (CONFLICTING: main hineinmergen); Funde, die der Prüfer nicht hatte, als „**Prüfer-Lücke:**“. Selbst genannte Lücken vor dem Nachtrag schließen oder gleichwertig begründen („Grenze“ nur, wenn unmachbar, mit Grund). Auflage „Umbau abtrennen“ erst gegen main prüfen (`git diff origin/main -- <Dateien>`). Vor „fertig“ selbst prüfen wie der Prüfer (`.claude/agents/pruefer.md`); Ziel ist Freigabe in Runde 1. Nur Hashes nennen, die auf origin liegen.
